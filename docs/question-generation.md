# Генерация вопросов: контракт Backend → ML v1

Рабочий внутренний endpoint: **`POST /api/v1/question-generation`**, JSON UTF-8,
`Content-Type: application/json`. Base URL внутри Docker: `http://ml-service:8001`.
Контракт реализован в FastAPI; это инструкция для интеграции Backend.

Генератор готовит черновики для административного контура. Он планирует пакет,
генерирует вопросы, критерии, шкалы и эталоны, проверяет их другой моделью,
исправляет дефекты и проверяет смысловые дубли. Записи в БД и публикацию выполняет
Core. ML не подключается к PostgreSQL и не создаёт пользовательские сущности.

Этот endpoint добавлен отдельно. Старый `/api/v1/question-bank/generate` сохраняет
прежний provisional DTO и детерминированную заглушку `[STUB]`; для новой интеграции
его использовать не нужно. Interviewer/Evaluator v2 и ASR не меняют контракт.

Обе схемы генерируются из Pydantic: `python -m app.contracts`;
`python -m app.contracts --check` проверяет синхронизацию. Неизвестные поля
отклоняются на всех уровнях. Имена полей — snake_case. Регистрозависимые значения
грейдов именно этого API — **`Junior`, `Middle`, `Senior`**; в runtime Evaluator
по-прежнему используются `junior`, `middle`, `senior`.

## Вход

```json
{
  "request_id": "b74ecff4-f1c3-4918-8d23-04a6425e330a",
  "specialization": "analytics",
  "area": "sql",
  "grade": "Middle",
  "count": 1,
  "comment": "Один узкий вопрос о COUNT и NULL в PostgreSQL, без сложной схемы таблиц.",
  "existing_questions": [],
  "bank_context_complete": true,
  "materials": []
}
```

| Поле | Требования |
| --- | --- |
| `request_id` | Обязательная строка UUID с дефисами. Core генерирует и сохраняет до HTTP-вызова. Один UUID обозначает одну логическую генерацию. |
| `specialization` | Только `analytics`, значение по умолчанию такое же. |
| `area` | Обязательная область, 1–120 символов после trim. Например `sql`, `etl`, `dwh`, `требования`, `интеграции`. Допускаются другие области. |
| `grade` | Обязательный минимальный грейд: `Junior`, `Middle` или `Senior`. |
| `count` | Строго integer 1–10, по умолчанию 3. Число вопросов, а не эталонов. |
| `comment` | Пожелание до 500 символов, по умолчанию пустая строка. |
| `existing_questions` | До 500 компактных записей банка, по умолчанию `[]`. |
| `bank_context_complete` | Boolean, по умолчанию false. Core подтверждает полноту контекста, а не просит ML загрузить БД. |
| `materials` | До 20 объектов `{id,text}`, по умолчанию `[]`. Содержимое материалов, не URL для скачивания. |

Предел сериализованного нормализованного запроса — **120000 UTF-8 байт**; предел
HTTP body до JSON-парсинга — **262144 байта**. Строки/boolean/float вместо integer
не принимаются. Дубли ID существующих вопросов или материалов запрещены.
Модели, ключи, цены, бюджет, timeout, `difficulty`, `topic` и `min_grade` не являются
полями запроса и не принимаются как скрытые параметры настройки.

Объект `existing_questions[]`:

| Поле | Требования |
| --- | --- |
| `id` | Обязательная непустая строка до 128 символов; стабильный ID из банка Core. |
| `text` | Обязательный текст вопроса, 1–8000 символов. |
| `area` | Обязательная область, 1–120 символов. |
| `skills` | До 10 непустых строк по 1–200 символов; по умолчанию `[]`. |
| `min_grade` | `Junior`, `Middle`, `Senior`; по умолчанию `Junior`. |

У материала `id` — непустая строка до 128 символов, `text` — 1–12000 символов.
Префикс ID `matrix:` зарезервирован для встроенного каталога. Не передавайте
эталоны, пользовательские ответы, персональные данные или полные рубрики старого
банка: для поиска дублей нужны вопрос, область и навыки.

Core выбирает компактный контекст целевой и смежных областей, включая черновики,
которые нельзя повторять. При неполном срезе нужно `bank_context_complete=false`.
ML не обрезает контекст молча и предупреждает об ограниченной проверке уникальности.
Содержимое материалов, comment и банка отделено от system-инструкций как данные.
Внешнего web-поиска и выполнения сгенерированного кода внутри генерации нет.

## Результат HTTP 200

Ответ содержит ровно `schema_version`, `job_id`, `status`, `questions`,
`rejected_candidates`, `warnings`, `metrics`. `schema_version="1.0"`,
`job_id` равен нормализованному UUID `request_id`.

| `status` | Значение для Backend |
| --- | --- |
| `completed` | Получено ровно count проверенных черновиков. |
| `partial` | Готовые черновики есть, но их меньше count. Сохранить полезную часть. |
| `failed` | Проверенных вопросов нет. Показать предупреждения и доступных кандидатов, не создавать искусственные вопросы. |
| `cancelled` | Результат кооперативной отмены библиотеки; полезная часть сохранена. При разрыве HTTP-соединения ответ доставить невозможно. |

**HTTP 200 не равен `status=completed`.** Сбой провайдера, недостаточный бюджет,
неудачный review или deadline после запуска возвращаются как терминальный
результат с предупреждениями и доступной полезной частью. Например 401/402
OpenRouter дают `status=failed` и warning `http_401`/`http_402`; это не ошибка
авторизации пользователя InterSim и не повод бесконечно повторять генерацию.

Каждый `questions[]` содержит:

- `id`: стабильный UUID, производный от job_id и позиции; это ID результата
  генерации, а не обещание использовать его как PK сущности Core;
- `text`: русский вопрос 20–2000 символов; `specialization="analytics"`, `area`;
- `min_grade`, `grades`: минимальный и все старшие грейды по порядку;
- `skills`: 1–4 конкретных навыка;
- `criteria`: 1–4 критерия с локальным `id`, нейтральным `description` и
  `grade_configs[]` (`grade`, положительный `weight` ≤10, `anchors[]`);
- `grade_configs[]` вопроса: (`grade`, `reference_answer`) для каждого грейда;
- `status="draft"`; `generation`: фактические модели writer/reviewer,
  `prompt_version`, исходный comment, material_ids, plan_target, результат
  автоматического review и при наличии distinctness_review.

Для Junior создаются эталоны/конфигурации Junior+Middle+Senior; для Middle —
Middle+Senior; для Senior — только Senior. Каждый критерий этого генератора
применим ко всем грейдам вопроса. Шкала новых черновиков — ровно **0, 1, 2**;
порядок полный, описания непустые. Границы 0/1 нормализуются кодом **до review**;
максимальные требования формулирует writer и сверяет независимый reviewer.
`max_score` получается как максимум anchors; отдельного `expected_level` нет.
Это подмножество модели банка: Interviewer/Evaluator продолжают поддерживать
другие полные шкалы `0..N` существующих вопросов.

`generation.quality_status="passed"` означает автоматический LLM-review, **не
одобрение человеком или публикацию**. Core сохраняет выбранные questions как
новые черновики QuestionVersion и проводит обычный review/publish workflow.
Взвешенный балл тренировки считает Core; веса не передаются Evaluator.

`rejected_candidates[]` — отдельные последние структурно корректные кандидаты,
`slot` с нуля, `quality_status=needs_revision|unverified`, конкретные `issues`.
Они не прошли полный цикл и не могут автоматически объединяться с questions.
При невалидном JSON вопрос наружу не выдаётся.

## Метрики и предупреждения

| `metrics` | Значение |
| --- | --- |
| `calls` | Физические попытки за весь job, включая ошибки и неопределённые после обрыва. Известные not_dispatched не входят. |
| `cost_usd` | Сумма известных `usage.cost`; отсутствие стоимости не выдумывается как бесплатный вызов. |
| `reserved_uncertain_usd` | Удержанный консервативный резерв для неизвестного исхода/стоимости. Это не второе независимое списание. |
| `elapsed_seconds` | Время с первого запуска job, включая перерыв перед восстановлением. Это не длительность текущего HTTP-запроса. |

Эти метрики формирует Python. Они не являются объектом `meta` MI-007 и не имеют
ограничения provider_attempts ≤2. Токены входа/выхода библиотека в этом контракте
не возвращает: если Core создаёт LlmCall, неизвестные токены должны оставаться
null. Не превращайте USD в токены и не суммируйте неизвестный резерв как точную
стоимость. Повтор сохранённого результата содержит накопленные прежние метрики;
учёт по job_id должен исключать повторное начисление этих же затрат.

`warnings[]`: `code`, русское `message`, необязательный `slot`.
Основные коды: `bank_context_incomplete`, `no_source_materials`,
`quality_attempts_exhausted`, `count_shortfall`, `planning_failed`,
`deadline_exceeded`, `budget_exhausted`, `context_limit`, `cost_uncertain`,
`cost_overrun`, `http_401`, `http_402`, `http_403`, `cancelled`.
Backend ветвится по code и status, а не по русскому тексту сообщения.

## HTTP-ошибки до результата

```json
{
  "error": {
    "code": "QGEN_JOB_BUSY",
    "message": "This question generation request is already running",
    "details": {
      "correlation_id": "b30f0085e90d4db49ccbe8dcfa3f745b",
      "request_id": "b74ecff4-f1c3-4918-8d23-04a6425e330a",
      "retryable": true,
      "retry_after_seconds": 2
    }
  }
}
```

| Код | HTTP | retryable | Действие |
| --- | --- | --- | --- |
| `QGEN_INVALID_INPUT` | 422 | false | Исправить DTO; провайдер не вызывался. |
| `QGEN_PAYLOAD_TOO_LARGE` | 413 | false | Уменьшить body. |
| `QGEN_UNSUPPORTED_MEDIA_TYPE` | 415 | false | Передавать application/json. |
| `QGEN_REQUEST_TIMEOUT` | 408 | true | Истёк лимит загрузки body 30 с; повторить с тем же UUID. |
| `QGEN_IDEMPOTENCY_CONFLICT` | 409 | false | UUID связан с другим payload, policy или версией промпта. Новая логическая операция требует нового UUID. |
| `QGEN_JOB_BUSY` | 409 | true | Этот UUID уже выполняется. Подождать; не создавать новый job. |
| `QGEN_CAPACITY_EXCEEDED` | 503 | true | Все слоты заняты; очереди внутри ML нет. |
| `QGEN_PROVIDER_NOT_CONFIGURED` | 503 | false | Исправить ключ/конфигурацию сервиса. |
| `QGEN_STORAGE_UNAVAILABLE` | 503 | true | Восстановить доступ к состоянию и повторять только тот же UUID. Не удалять журнал для обхода ошибки. |
| `QGEN_INTERNAL_ERROR` | 500 | false | Диагностика по correlation_id, без автоматического нового job. |

Для JOB_BUSY/CAPACITY_EXCEEDED возвращаются `Retry-After: 2` и согласованное поле
details. `X-Correlation-ID` присутствует на всех ответах. request_id в details
может отсутствовать, если тело ещё не прошло валидацию. Ошибки не содержат
request body, эталонов, ключей, provider payload или stack trace.

## Выполнение и идемпотентность

ML **ожидает результат** в одном HTTP-запросе. В ML нет 202/polling API, фоновой
очереди, скрытого выполнения после disconnect или записи в БД Core.
Рекомендуемый поток административного UI:

1. Core проверяет права администратора, создаёт свой job и стабильный UUID,
   сохраняет исходный payload, возвращает своему UI 202.
2. Фоновый worker Core вызывает POST ML с этим UUID. Для генератора используется
   **отдельный HttpClient с timeout 960 с** при штатном ML-бюджете 900 с.
   Клиент MI-007 с timeout 60 с для этой операции не подходит.
3. Core сохраняет status, questions, rejected_candidates, warnings и metrics,
   показывает полезную часть пользователю. Выбранные вопросы добавляет в банк
   одной транзакцией как draft и повторно проверяет уникальность.
4. Для transport retry worker отправляет тот же UUID и **тот же payload**.
   Завершённые completed/partial/failed результаты возвращаются из журнала
   без LLM. Чтобы намеренно заново сгенерировать после failed/partial, Core
   создаёт новый job/UUID и учитывает, что это новый платный запуск.
5. Для отмены worker отменяет активный HTTP-вызов своим CancellationToken,
   который принадлежит job, а не уже завершённому запросу UI, вернувшему 202.
   ML отменяет provider task, сохраняет доступный журнал и освобождает слот.
   Уже полученный провайдером запрос может быть оплачен.

После падения процесса незавершённый job возобновляется тем же POST. Сохранённые
ответы переиспользуются, бюджет/дедлайн не обнуляются. Для неизвестного исхода
удерживается резерв; библиотека может перейти к следующей ограниченной попытке
в оставшемся бюджете. Exactly-once billing внешнего провайдера не гарантируется.
Во время обновлений завершайте jobs старой версией либо сохраняйте их policy
и prompt_version: изменение fingerprint корректно даёт конфликт.

Режим рассчитан на **один Linux-host и общее локальное постоянное хранилище**
всех ML workers. По умолчанию допускается одна генерация; файловые блокировки
координируют несколько процессов на этом хосте. Для нескольких независимых
хостов нужны sticky routing/общее состояние и распределённые блокировки —
это не реализовано. Не удаляйте volume или журнал при обычном redeploy/retry.

## Серверные настройки и Docker

| Настройка | Штатное значение |
| --- | --- |
| `QUESTIONGEN_API_KEY` | Пусто → использовать OPENROUTER_API_KEY. Можно выделить отдельный ключ. |
| `QUESTIONGEN_STATE_DIR` | Локально artifacts/question-generation; в Compose /var/lib/intersim/question-generation. |
| `QUESTIONGEN_MAX_CONCURRENT` | 1 на общий каталог одного хоста. |
| `QUESTIONGEN_POLICY__MAX_COST_USD` | $1.00 на пакет. |
| `QUESTIONGEN_POLICY__DEADLINE_SECONDS` | 900 с на цикл, до 3600 в допустимых настройках. |
| `QUESTIONGEN_POLICY__CALL_TIMEOUT_SECONDS` | 90 с на один provider call. |

Writer: `anthropic/claude-sonnet-5.5`; технический fallback writer:
`google/gemini-3.8-flash`; независимый reviewer: `openai/gpt-5.6-luna`.
Это отдельные GenerationSettings, не OPENROUTER_MODEL Interviewer/Evaluator.
Review другой модельной семьи обязателен. Провайдеры выбираются OpenRouter
в пределах заданных price caps. Содержательные исправления делает основной
writer; fallback используется для ограниченного сетевого/форматного восстановления.

По умолчанию — 3 содержательных варианта позиции и 2 попытки этапа; планирование
один раз на пакет; dedicated distinctness при наличии контекста. Для штатной
policy верхняя граница — 2 + 18×count обращений, но время и бюджет ограничивают
цикл раньше. Настройки и цены не принимает административная форма. Другие поля
GenerationSettings можно задать nested environment при прямом запуске; Compose
передаёт только явно перечисленные переменные. При изменении моделей/ценовых
ограничений добавьте соответствующее environment в свой Compose override и
повторите opt-in canary. Не меняйте конфигурацию уже выполняющегося job.

Compose добавляет только для генератора named volume `questiongen_state`.
Каталог создаётся в Docker-образе с UID/GID 1000 и mode 0700, журналы — 0600;
основная файловая система контейнера остаётся read-only. Каталог содержит
черновики, эталоны и материалы: доступ и backup должны быть закрытыми.
Срок хранения определяет инфраструктура/Core; удаление журнала снимает защиту
от повторной оплаты. `docker compose down` сохраняет volume; не используйте
`down -v` для обычного обновления. Штатные shutdown 60/75 с могут отменить
длинную генерацию: перед обновлением дренируйте задания или возобновляйте их
тем же UUID и совместимой версией после перезапуска.

## Проверка и происхождение

Перенесена самостоятельная папка `questiongen/generation` из соседнего проекта,
вместе с catalog.json; она размещена в `app/question_generation`, потому что
`app/generation.py` уже обслуживает MI-007. Старый офлайн-пайплайн, CLI, секреты,
исторические журналы и зависимости его сборки не включены. Исходный рабочий
репозиторий не изменён. [Manifest снимка](reference/questiongen-source.json)
фиксирует source commit и хеши файлов, включая незакоммиченный upstream-модуль.
Runtime-зависимостей сверх уже установленных Pydantic/HTTPX не добавлено.

```bash
python -m pytest
python -m app.contracts --check
ruff check .
ruff format --check .
# Отдельный платный canary: до $0.35, один вопрос, до 180 с.
python -m pytest -m integration tests/test_question_generation_live.py
```

Штатные тесты не обращаются к провайдеру. Перенесены 76 behavioral tests движка
и клиента; HTTP-тесты проверяют реальные FastAPI-ответы по двум JSON Schema,
лимиты ввода, ошибки, блокировки между экземплярами, частичный результат,
идемпотентность после пересоздания сервиса и отмену по настоящему ASGI disconnect.
Адаптеры результата проверяются входными DTO существующих Interviewer/Evaluator.
Каталог включён и в Docker, и в wheel.

Зафиксированный реальный пример: один reviewed draft, 3 provider calls,
$0.028031 известной стоимости, 21.038 с; повтор без новых provider calls.
Это результат одного canary, а не гарантия качества всех будущих вопросов.
Автоматический review остаётся вероятностным; окончательное решение о публикации
принадлежит вашему процессу проверки.
